# Формат `.ewb`

Документ описывает формат, который использует Electronics Workbench 5.12.
Сведения получены реверс-инжинирингом приложения и проверены на файлах,
созданных самой EWB. Сервер не требует установки EWB.

## Два уровня

Файл `.ewb` состоит из двух уровней:

1. **Контейнер** — текстовый заголовок, пара-кодирование, сжатые блоки и
   контрольная сумма.
2. **Документ** — текстовая древовидная структура `Project_5_1` с блоками
   `Block`/`Document`, элементами и проводами.

Оба уровня разбираются и собираются отдельно. Это позволяет проверять
контейнер и документ независимо.

## Контейнер

### Заголовок

Заголовок — текст Latin-1 с CRLF. Пример:

```text
Electronics Workbench Circuit File\r\n
Version: 5\r\n
Charset: ANSI\r\n
Description: \r\n
"RC + LED" \r\n
\r\n
EncryptionType: 2\r\n
UsingVectorGraphics: 0\r\n
/
```

Важные детали:

- после `Description: ` идёт отдельная строка с описанием в кавычках;
- после закрывающей кавычки стоит пробел;
- `EncryptionType: 2` — не шифрование, а обозначение используемого
  кодирования/сжатия;
- заголовок заканчивается символом `/` без перевода строки;
- все строки заголовка, включая последнюю перед `/`, разделены CRLF.

Сервер сохраняет исходный заголовок при редактировании. При создании нового
файла заголовок собирается функцией `ewb_codec.make_header`.

### Пара-кодирование

Полезная нагрузка после `/` кодируется по два символа на байт:

```text
c1 = (byte >> 3) + 0x30
c2 = 4 * (byte & 7) + 0x30
```

Символ `$` (0x24) завершает каждый сжатый блок, включая последний. Символ
`!` (0x21) завершает всю закодированную последовательность. После `!` идут
8 шестнадцатеричных цифр контрольной суммы в нижнем регистре.

Перевод строки вставляется после каждых 65 символов всей
последовательности — включая `$`, `!` и цифры контрольной суммы. В конце
файла завершающего перевода строки нет.

При чтении CR и LF удаляются **до** разбора пар, потому что перевод строки
может попасть между `c1` и `c2`.

### Сжатые блоки

Документ делится на блоки по 1024 байта. Каждый блок сжимается вариантом
PKWARE implode/DCL:

- первые два байта: режим литералов (0) и код словаря (4..6);
- биты читаются LSB-first;
- флаг 0 — литерал, 8 бит данных;
- флаг 1 — совпадение, длина кодируется 16-символьной таблицей, расстояние —
  64-символьной;
- конец блока — длина 519 (символ 15 плюс 8 дополнительных бит `0xFF`).

Сервер умеет писать как LZ-блоки (`compress_lz_block`), так и блоки только из
литералов (`compress_literal_block`). Оба варианта декодируются EWB.

### Контрольная сумма

Алгоритм:

1. Документ делится на куски по 1024 байта.
2. Для каждого куска считается CRC-32 (отражённый полином `0xEDB88320`,
   начальное значение `0xFFFFFFFF`, без финального XOR).
3. CRC каждого куска побитово инвертируется.
4. Все инвертированные значения складываются по XOR.
5. Результат печатается как `%08x`.

Контрольная сумма считается по **несжатому** документу, а не по контейнеру.

## Документ `Project_5_1`

Документ — текст Latin-1 с CRLF. Каждый блок:

```text
<отступ><имя> \r\n
<отступ>{ \r\n
...дочерние блоки и строки...
<отступ>}
```

Особенности форматирования:

- заголовок блока и открывающая скобка заканчиваются пробелом;
- строки полей заканчиваются пробелом;
- закрывающая скобка пробела не имеет;
- отступ — два пробела на уровень;
- порядок полей и блоков важен для байтового совпадения.

Парсер сохраняет все незнакомые строки и блоки дословно. Поэтому
неотредактированные части файла воспроизводятся байт-в-байт.

### Структура

Минимальная структура нового файла:

```text
Project_5_1
  CircuitHeader
    InternalCircuitVersion i 511
    ZoomFactor i 100
    VersionSpecific
      SerialNo R ""
      Version R "Version 5.12"
    Library
      Name R "$"
    PrintSettings
      ...
  Circuit
    Preferences
      ...
    Elements
    Wires
```

Реальный файл EWB может содержать дополнительные блоки: настройки
инструментов, геометрию окна, параметры анализа. Сервер их не удаляет.

### Элементы

Элементы лежат в `Circuit/Elements`. Поддерживаются блоки:

- `Comp` — обычный компонент;
- `Instrument` — измерительный прибор;
- `ExtComp` — внешний компонент/подсхема.

Основные поля `Comp`:

```text
Comp
{
  PartNum i 1
  Position i:3 1 500 460
  Value r:5 1000 0 0 0 0
  ModelUnits i:5 1 0 0 0 0
  Common
  {
    RefID A "R1"
  }
  ModelName R ""
  Status i 0
}
```

- `PartNum` — номер в каталоге EWB, поддерживается диапазон 0..39. Полный
  список всех 40 записей — в [`CATALOG.md`](CATALOG.md).
- `Position` — три целых: код поворота 0..7, `x`, `y`.
- `Value` — массив вещественных; число элементов зависит от детали.
- `ModelUnits` — единицы модели.
- `ModelName` — имя модели, если поле есть у детали.
- `Status` — статус, обычно 0.
- `Common/RefID` — обозначение. У земли всегда `"0"`, поэтому несколько
  земель различаются только индексом элемента.

Некоторые детали имеют дополнительные блоки. Например, у управляемого
источника `PartNum 7` есть `IndependentSourceParameters`, а у `NODE`
(`PartNum 39`) — поля `m_tptrElem`, `m_flags`, `m_i_cond`, `m_i_ni`.

Сервер создаёт компоненты по шаблону, восстановленному для каждого PartNum, и
не копирует блоки из пользовательских файлов.

### Провода

Провода лежат в `Circuit/Wires`:

```text
wire
{
  pos i:4 2 1 3 0
  segs i:4 1 70 2 20
  colour i 0
  wire_id i 0
  node_p A "0"
  x_factor r 1
  y_factor r 1
}
```

- `pos i:4 a pa b pb` — элемент `a`, вывод `pa`, элемент `b`, вывод `pb`.
- `segs` — необязательный массив пар `[direction, length]`. Если поля нет,
  EWB строит маршрут сама. Это допустимое состояние, а не ошибка.
- `colour` — цвет.
- `wire_id` — идентификатор.
- `node_p` — текстовая метка цепи.
- `x_factor`, `y_factor` — масштабные коэффициенты, обычно 1.

Коды направлений:

| Код | Смещение |
|---|---|
| 1 | +x |
| 2 | +y |
| 4 | -x |
| 8 | -y |
| 3 | +x, +y |
| 6 | -x, +y |
| 9 | +x, -y |
| 12 | -x, -y |

Маршрут хранится относительно вывода `a`. Если известна только позиция
вывода `b`, сервер проходит сегменты в обратном порядке.

### Выводы

Абсолютная координата вывода:

```text
pin_abs = (Position.x, Position.y) + offset(PartNum, rotation, pin)
```

Смещения хранятся в `ewb_parts.PINS` и восстановлены из геометрии проводов в
файлах, созданных приложением. Известны не все сочетания «деталь + поворот».
Если сочетания нет:

- компонент можно создать;
- координаты его выводов неизвестны;
- новый провод сохраняется без `segs`;
- при перемещении существующего провода маршрут удаляется, чтобы EWB
  перестроила его сама.

Это осознанное поведение: лучше оставить маршрутизацию приложению, чем
записать неверную геометрию.

### Цепи

`ewb_read_schematic` строит цепи объединением выводов, соединённых проводами
(union-find). `node_p` не влияет на связность: это метка, которая попадает в
`node_labels`. Два провода с одинаковым `node_p`, но без общей точки, не
считаются одной цепью.

## Совместимость

Сервер придерживается следующих правил:

- не добавляет поля и блоки, которых нет в формате;
- сохраняет заголовок и порядок существующих блоков;
- использует `Comp` для всех создаваемых компонентов;
- пишет `Value` и `ModelUnits` с теми же типами и количеством элементов, что
  и EWB;
- не пишет `segs`, если геометрия неизвестна;
- сохраняет `EncryptionType: 2`;
- пересчитывает контрольную сумму после каждого изменения;
- делает резервную копию `.bak` перед записью.

Проверка `ewb_validate` возвращает три ключевых флага:

- `document_roundtrip_exact` — документ после разбора совпадает с исходным;
- `container_roundtrip_exact` — контейнер можно собрать повторно;
- `checksum_matches` — контрольная сумма соответствует документу.

Для редактируемых файлов требуется `document_roundtrip_exact`. Если он
`false`, сервер отказывается изменять файл.

## Ограничения

- Каталог компонентов ограничен PartNum 0..39.
- Геометрия выводов известна не для всех поворотов.
- `ExtComp` и `Instrument` читаются, но создание новых инструментов не
  реализовано.
- Сложные подсхемы и иерархические проекты могут содержать блоки, которые
  сервер сохраняет, но не интерпретирует.
- SVG-превью приблизительное.
- Формат восстановлен по EWB 5.12; другие версии могут отличаться.

## Проверка формата вручную

Разобрать контейнер и вывести документ:

```bash
python3 scripts/ewb_codec.py "local/examples/лаба 4.ewb"
```

Проверить байтовый round-trip документа:

```bash
python3 scripts/ewb_codec.py "local/examples/лаба 4.ewb" > /tmp/document.txt
python3 scripts/ewb_doc.py /tmp/document.txt
```

Ожидаемый результат второй команды:

```text
bytes N -> N, exact True
```

Файл `local/examples/лаба 4.ewb` не входит в репозиторий и должен лежать
локально.
